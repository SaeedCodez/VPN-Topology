# CLAUDE.md — how to work in this repo

VPN Topology is a **read-only** live map of a production VPN system with paying
users (Remnawave panel, Relay 1, XBridger, Mullvad, France exit). The map is
described by files in `topology/`; the hub loads them, observes the servers and
shows the same facts on the board (web) and in the `vpnmap` CLI.

## Rules (read first, always)

1. **The map only observes.** Nothing in this repo — hub, CLI, agent, you — may
   change, restart or reconfigure a VPN server. Real changes stay with
   Remnawave, `relay-ctl` and XBridger, and need the owner's approval.
2. **Never print, commit or paste secrets.** No tokens, passwords, keys,
   `privateKey`, `shortIds` or `.env` values in files, commits, PRs or chat.
   Secrets live only in the hub's env vars (Coolify) or on the servers.
   `vpnmap validate` rejects lines that look like secrets.
3. **Do not install anything on a production server yourself.** Print the exact
   commands (`vpnmap agent install-cmd <node>`, `vpnmap plan`) for the owner.
4. **`vpnmap apply` only after the owner approved the plan you showed.**
5. **Never edit `topology/layout.yaml`.** The UI writes positions; the owner runs
   `vpnmap layout pull` to commit them.
6. **Update Notion after every change to the map** (Notion rule 7): run
   `vpnmap docs` and paste the result into page 01 · Architecture & Traffic
   Flows, and add a Changelog line on the VPN Infrastructure page.
7. Inspect before you change anything; when unsure, ask.

Source of truth for the VPN itself: Notion page "VPN Infrastructure"
(https://app.notion.com/p/3f828d2a9e9b8115bba4ee2a8a69c8fc) and its children
01 (flows), 02 (servers), 07 (runbook), 08 (known issues), 09 (XBridger).
Follow its "Rules for agents".

## Repo layout

```
topology/map.yaml             groups, settings, observation sources (probe)
topology/components/*.yaml    one file per feature: nodes, links, routes, checks, alerts, docs
topology/layout.yaml          node positions (UI only; agents never edit)
schema/*.schema.json          generated by `vpnmap schema` from pkg/topology (do not hand-edit)
pkg/topology                  the only YAML parser/validator; collector catalog; alert expressions
pkg/agentcfg, pkg/protocol    agent config file and agent → hub push payload
pkg/redact                    secret redaction shared by CLI and agent
apps/cli                      `vpnmap` (Go)
apps/agent                    `vpnmap-agent` (Go), deploy/ has units, install/uninstall, checks.d examples
apps/hub                      NestJS hub: ingest, resolvers, evaluation, root cause, alerts, API, WebSocket, demo simulator
apps/web                      Nuxt 3 board (Vue Flow, Tailwind, ECharts); types come from apps/hub/src/contract.ts
.claude/skills                add-component, diagnose-outage
```

## Workflow: "I added X to the VPN, add it to the map"

Use the `add-component` skill. In short:

1. **Read** the Notion pages for X (server page under 02, the flow in 01, 08 for
   known issues). Ask the owner for anything missing (IP, ports, which squad).
2. **Discover**: `vpnmap discover` (phase 2) lists live things the files don't
   declare and drafts YAML. Until then: `vpnmap get agents`, the board's Drift
   panel, and `vpnmap describe <node>` show undeclared listening ports.
3. **Edit one component file**: a new feature → `vpnmap new component <name>`;
   a change to an existing feature → edit its file. Reference existing node ids
   from other components; don't duplicate nodes.
4. `vpnmap validate` — fix every error (each names the file, line and fix).
5. `vpnmap plan` — shows the diff against the live map and what must be
   installed on servers (agents, local checks, agent config, nft counters).
6. **Show the plan to the owner and wait for approval.** Commit the file.
7. `vpnmap apply -m "<what and why>"` (refuses uncommitted topology files).
8. `vpnmap docs` → update Notion page 01 + Changelog.
9. Give the owner the server-side commands from the plan (never run them).

## Topology format (quick reference)

- Ids: lowercase, digits, dashes (`relay-2`). Unique across all components.
- Node: `id, name, kind, group, address, role, agent, docs, facts, checks,
  metrics, card (≤3 ids), runbook`. Kinds: users relay panel vpn-node bridge
  exit cdn edge vpn-provider internet router server storage service.
- Link: `id, label (E3), title, from, to, plane (data|control), protocol,
  traffic, conns, health, docs, notes, runbook`. `up` = bytes from → to.
- Route: ordered `hops` (link ids) from the users to an exit, `users`
  (live collector) / `users_estimate`, `squads`, `probe`, `impact`
  (outage|degraded). Root cause = first failing hop of a broken route.
  A broken route serving a squad listed in `settings.critical_squads`
  (map.yaml) turns the whole board red.
- Check = `{ collector: <name>, ...params }` from the **closed catalog**:
  `vpnmap explain collector` lists them, `vpnmap explain collector <name>`
  shows parameters + example. `on_fail: degraded` makes a failure amber.
- Collectors on a server (`host:` / `from: <node>`) need `agent: true` on that
  node; the agent's local config is generated by `vpnmap agent config <node>`.
  The hub never sends commands to agents. A `local-check` only references a
  script that already exists in `/etc/vpnmap-agent/checks.d/` on that server.
- Alerts: `when: "link.wg-game.health == down for 2m"`; refs are
  `node|link|route.<id|*>.<field>`, `<kind>.<id>.check.<check id>.<field>`,
  `collector.<name>.<field>`; values `ok|degraded|down|unknown`, `true|false`,
  numbers with units (`5s`, `80%`, `10Mbps`); `and`, `or`, `not`, `for 3 samples`.
  `message_fa` (Persian, required) goes to Telegram; `{name}` is the entity.
- Runbook commands must be read-only (validate rejects restart/stop/rm/apply…).

## Reading the live system (same facts as the board)

`vpnmap status`, `get nodes|links|routes|alerts|components|agents`,
`describe <id>`, `events --since 2h`, `metrics <id> --since 1h`,
`snapshot --at <time>`, `diagnose`, `path users france-exit`, `why <id>`.
Every command takes `--json` (use it when you parse output) and read commands
take `--at 2026-10-22T02:03Z` or `--at -2h`. Exit codes: 0 healthy,
1 degraded, 2 down, 3 invalid input. For outages use the `diagnose-outage` skill.

## Developing

```bash
go build -o bin/vpnmap ./apps/cli && ./bin/vpnmap validate
pnpm install
pnpm --filter @vpnmap/hub dev          # demo hub on :4000 (simulator, auth off, in-memory DB)
pnpm --filter @vpnmap/web dev          # board on :3000, proxies /api and /ws to :4000
VPNMAP_HUB=http://localhost:4000 ./bin/vpnmap status
```

Demo mode replays the real incidents (2026-10-13 :9000 closed after node 3
reboot; 2026-10-20/22 rw-api hang while healthy). `vpnmap demo play <id>` or
the board's "Replay incident" menu starts one live.

Tests: `go test ./...`, `pnpm --filter @vpnmap/hub test` (replays incidents and
asserts the root cause), board: `vue-tsc` + `nuxi generate`. CI runs
`vpnmap validate` on every PR.

Code style: TypeScript strict, small pure functions for evaluation (no I/O in
`apps/hub/src/engine`), NestJS only at the edges; Go with the standard library
where possible; comments explain *why*. Changes to the collector catalog go to
`pkg/topology/catalog.go` + the resolver in `apps/hub/src/engine/resolve.ts`
(+ the agent if it runs there) + `vpnmap schema`. Names derived from check keys
(nft counters, ss/http/log ids) must stay identical in `pkg/topology/ids.go` and
`apps/hub/src/engine/ids.ts` (both have tests).
